# تشغيل MangaDex على المضيف — 24 أكتوبر 2026

## النتيجة الحالية

اجتاز مرشح MangaDex المعاد بناؤه من المصدر العام تشغيلًا فعليًا داخل محمّل
MSL المتحقق على Linux. نجحت خمس حالات دون شبكة وتسع حالات في المسار المباشر:

| الفحص | النتيجة |
| --- | --- |
| تثبيت SourceFactory | تسجيل المصادر الـ61 ومطابقة IDs واللغات مع metadata |
| بدء المصدر | إنشاء headers وعميل الضغط الحقيقيين عبر خدمات المضيف |
| إعدادات المصدر | 12 صفًا، مع رفض UUID غير صالح وقبول قيمة صحيحة |
| التصفح | 20 عنوانًا من popular |
| البحث والتفاصيل والفصول | نتيجة بحث واحدة و9 فصول للعنوان المختار |
| روابط الصور | حل روابط 23 صفحة وتجديد رابط بختم زمني منتهٍ |
| الإزالة | انتظار تحرير العمليات وإغلاق الأرشيف المتحقق |
| المدخل الثابت | configure/load/sources/unload/close مع تحقق الحزمة وتسجيل 61 مصدرًا |
| عقد التطبيق JSON | popular → update → pages مع حفظ metadata؛ 9 فصول و23 صفحة |

هذه أعداد جلسة واحدة، وليست توقعًا ثابتًا لبيانات الموقع. لم يُحمّل محتوى
الصور أو يُعرض قارئ iPhone في هذا الفحص. الأدلة ومدخلاتها وأوامرها:
[دون شبكة](../validation/mangadex-source-host.json) و
[الشبكة المباشرة](../validation/mangadex-source-live-host.json).
اجتازت أيضًا [17 حالة HTTP/TLS مؤلفة](../validation/runtime-network-host.json)،
ومنها حالة جديدة تفرض استخدام imageRequest المخصصة مع بقاء بيانات الصفحة
كما هي، إضافة إلى حالات الإلغاء وأخطاء TLS السابقة.

## التغييرات التي مكّنت التشغيل

أضيفت ست تبعيات runtime مع بصمات SHA-256 وSHA-512 ورخص معلومة:
OkHttp Brotli/Zstd 5.4.0، وBrotli decoder 0.1.2، وJsoup 1.22.2،
وJSON-Okio 1.11.0، وJSpecify 1.0.0. لا تحمل هذه الملفات الست مكتبات أصلية
أو native methods وفق الفحص الثابت؛ Zstd نفسها تبقى مكتبة المشروع المبنية
من المصدر مع JNI. [جرد التبعيات](../validation/runtime-extra-dependency-review.json).

نُفذت مساعدات `Build.VERSION.RELEASE` و`SystemClock` و`Log` المطلوبة من
المصدر. يمرر المضيف إصدار المنصة وhttp.agent قبل إنشاء المصدر. القيمة
`26.2` في هذا الاختبار مدخل محاكاة صريح؛ التنفيذ نفسه على Linux، وليس iOS.
يجب أن يمرر تطبيق الهاتف إصدار الجهاز الحقيقي عند الربط.

كشف طلب الصفحات أن `Page.imageUrl` مسار نسبي، وأن `Page.url` تحمل بيانات
الخادم وطلب التجديد والوقت. صُحح `HttpSource.getImageUrl` ليستدعي
`imageRequest` الخاصة بالمصدر على dispatcher للإدخال والإخراج. لا تُعدّل
حقول الصفحة الخام، كي تبقى معلومات التجديد متاحة. اجتاز المصدر الفعلي حل
الروابط الجديدة وتجديد رابط منتهي. لا يعيد هذا الاستدعاء headers أو جسم
طلب الصورة إلى Swift؛ يجب أن يستهلك تنزيل الصور طلب المصدر وعميله كاملين.

## المتبقي قبل IPA الاختبار

1. تنفيذ واجهة أوامر المضيف إلى Swift مع تحويل نماذج العناوين والفصول
   والصفحات داخل مدة حجز المصدر، وحفظ memo وتحويل تواريخ الفصول من ms إلى s.
2. توصيل coordinator ومخزن الحزم والثقة بالمحمّل الحقيقي، واستخدام استجابة
   JNI المملوكة بدل مخزن Swift الحالي ذي 16 KiB.
3. ربط JVM ومكتبة Zstd وتغليف JAR المضيف وتبعياتها وإشعارات تراخيصها في تطبيق MSL الرئيسي،
   وإثبات النقل وTLS وتنزيل الصور بطلب المصدر على iOS.
4. بناء IPA غير موقعة عبر Actions وفحصها، ثم توقيعها واختبارها على iPhone:
   مستودع ← إضافة ← بحث ← تفاصيل ← فصول ← صور، مع الإلغاء وإعادة التشغيل.

لم يُختبر إلغاء تجديد التوكن المتزامن في هذا التشغيل؛ الطلب المتزامن يبقى
داخل حجز المصدر حتى ينتهي، وقد ينتظر مهلة HTTP. فلاتر MangaDex التي تطلق
عملًا عبر GlobalScope تحتاج تحققًا مستقلًا لعمرها أثناء إزالة الحزمة.
لا يُعد نجاح الإزالة هنا دليلًا على تفريغ كل class أو خيط قد تنشئه الإضافات.

أنتجت متابعة [جسر التطبيق](SOURCE-RUNTIME-JSON-AR.md) IPA للتحقق من بناء
Swift والرموز، لكنها لا تحمل JVM أو JAR المضيف بعد؛ ليست نسخة تشغيل إضافات.
مطابقة الواجهة والخلفيات والخطوط وجميع الإعدادات والنسخ والاستعادة ما زالت
مطلوبة في [TODO](../TODO.md)، وWi-Fi مؤجل.

```bash
python3 scripts/check-mangadex-host.py --candidate-directory build/mangadex-source-39768470880/evidence
python3 scripts/check-mangadex-host.py --candidate-directory build/mangadex-source-39768470880/evidence --live --reuse-host-build
```

لا يقبل reuse تغيير مدخلات إنتاج JAR أو ملف البناء أو قفل التبعيات أو بصمة
JAR الناتجة. يستخدم التشغيل المباشر إعداد proxy الموروث دون تعطيل تحقق TLS.
