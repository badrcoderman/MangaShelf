# محرك Tachimanga: أدلة وخطوة التنفيذ

## النتيجة
العينة تشير إلى OpenJ9 مع آثار بناء JDK17، وليست دليلًا على استخدام HotSpot Zero. توجد دالة `_J9_CreateJavaVM` معرفة داخل قسم الكود في الملف التنفيذي الرئيسي، ومعها دوال `JNI_OnLoad_java/net/nio/zip/verify/prefs/sqlitejdbc` وغيرها. هذا يدعم استنتاج ربط مكونات Java داخل التطبيق؛ لا يحدد وحده إعدادات الرابط الكاملة.

`RUNTIME-REFERENCE.json` يحفظ أسماء الرموز وطرق JavaLauncher وعناوين خيارات الإقلاع من المستخرجات. يمكن إعادة الجرد باستخدام `scripts/inspect_runtime_reference.py <organized-extraction>`.

## الإقلاع والبيانات
- `JavaLauncher.launchJVM:`: نقطة إطلاق مرصودة، مع خيارات `-Xint` و`-Djava.compiler=NONE`.
- `-Xms128M` و`-Xmx256M`: قيم افتراضية مرصودة مع مسارات إعدادات Xms/Xmx؛ ليست قياسات للاستهلاك الفعلي أو سقف ذاكرة التطبيق كله.
- `-Xshareclasses:none` و`-XX:-OpenJ9CommandLineEnv` و`-Dcom.ibm.tools.attach.enable=no`: إعدادات OpenJ9 مرصودة لا تنقل عميانيًا إلى HotSpot.
- `jre/lib/modules`: صورة مكتبة Java بفهرس 63 وحدة. لم يثبت احتياج الخلفية لكل وحدة.
- `MCHome.bundle/res.zip`: حزمة أصناف الخلفية، ويظهر المسار في إعداد classpath.
- `suwayomi/tachidesk/MainKt.main(String[])`: نقطة دخول الخلفية المرصودة.
- توجد طرق startServer/startSocket/stopSocket/waitRequestDone/javaChannel:content:؛ دورة الحياة تتجاوز إنشاء JVM فقط.

توثيق OpenJ9 الرسمي يشرح أن `-Xint` يعطل JIT وAOT وينفذ بالتفسير: https://eclipse.dev/openj9/docs/xint/ . وجوده في خيارات الإقلاع يدعم اعتماد المسار التفسيري، لكنه ليس قياس تشغيل حي ولا يثبت سرعة كل مصدر.

المشروع العام للمحرك: https://github.com/eclipse-openj9/openj9 . وجود هذا المستودع لا يعني أن تعديلات iOS الخاصة بالعينة موجودة فيه. آثار `OpenJ9_iOS_SDK` ومسارات البناء ليست سورس SDK قابلًا لإعادة البناء.

## ما يعنيه لمشروعنا
محاولة OpenJDK Mobile Zero الحالية بديل تجريبي؛ ليست محرك Tachimanga نفسه. لا يوجد حتى الآن ناتج iOS متحقق التشغيل. يلزم إثبات بناء محرك مناسب من المصدر، وصورة مكتبة متوافقة معه، وربط JNI ودوال النظام المطلوبة. لا يصح خلط صورة jre من العينة مع محرك مختلف وافتراض التوافق.

أضفنا `runtime-probe/` بملفي Java من كتابتنا و`scripts/run-runtime-probe.py`. الاختبار يحمّل صنفًا من JAR منفصل عبر URLClassLoader، ثم يتحقق من reflection وUnicode وخيط عمل وGZIP والملفات. يبني إلى Java 17 ويعمل بـ-Xint. ليس إضافة Tachiyomi حقيقية، ولا يشغّل كود العينة.

يمكن استدعاء `mangashelf.probe.RuntimeProbe.run(String,String)` من حاضنة JNI المستقبلية على iOS. قبل ذلك، نجاحه على المضيف يثبت صلاحية الاختبار وبعض قدرات VM المضيف فقط.

## بوابات الانتقال
1. بناء ARM64 iOS والتحقق من نوع المنصة والربط، وليس اسم ARM64 فقط.
2. بدء JVM داخل تطبيق iPhone ثم نجاح probe مع JAR منفصل ودليل نتيجة على الجهاز.
3. تنفيذ الجسر المطلوب للمصدر التجريبي: الشبكة والكوكيز والملفات وأي JNI مستخدم فعلًا.
4. تنفيذ البحث والتفاصيل والفصول والصفحات باستخدام إضافة فعلية، ثم فحص الاستقرار ودورة الحياة.

النتيجة الحالية: لدينا معلومات مفيدة ومحددة عن المحرك واختبار مستقل قابل للنقل. لا يوجد بعد إثبات تشغيل المحرك على iPhone أو اكتمال المرحلة الثانية.
