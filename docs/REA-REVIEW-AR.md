# دراسة REA وتطوير مسار الإضافات

تاريخ الدراسة: 19–20 أكتوبر 2026. نقطة البداية: MangaShelf عند `23f95feb5cf06aaee47b93391f5a05a2bbe9850c`، على فرع عمل مستقل `improve/rea-runtime-contract`.

## النتيجة العملية

استُخدم REA **فعليًا** لجرد حزمتي JAR المنشورتين مع خلفية Tachimanga، ثم قورن عقد الاتصال في السورس العام بتنفيذ MangaShelf. كشفت المقارنة مشاكل في صدق نتائج المحرك، ترميز الأوامر، حفظ روابط المصادر، وحالات الفشل عبر C/JNI. التغييرات هنا تعالج هذه المشاكل؛ لا تنفذ JVM كاملًا ولا تثبت تشغيل إضافة على iPhone.

عينة Tachimanga المذكورة في `AGENT.md` غير موجودة في checkout الحالي، ولم تُعثر عليها بالبحث المتاح عن الملفات. لذلك **لم يُفحص ملف التطبيق التنفيذي أو IPA في هذه الجولة**. لا تُنسب تقارير الدراسة القديمة إلى تشغيل REA الجديد.

## المصادر والأدلة

- [REA](https://github.com/morluto/rea): نسخة السورس `b4938aed58737293a6987630476632619713f5cd`؛ الأوامر المنفذة من `rea-agents@6.7.0` عبر CLI، دون تعديل إعدادات العميل.
- [خلفية Tachimanga العامة](https://github.com/tachimanga/Tachidesk-Server/tree/2e52214106ffab02d13ff61a620def78414a8a45): مراجعة `2e52214106ffab02d13ff61a620def78414a8a45`، مطابقة للمراجعة المثبتة سابقًا في المشروع. ليست سورس واجهة التطبيق بأكملها.
- `validation/rea/provenance.json`: مراجعات المستودعات وبصمات الملفات التي روجعت.
- `validation/rea/sqlite-jdbc-inspection.json` و`cloud-api-inspection.json`: ناتج REA الكامل، بما فيه التغطية والقيود، دون نسخ أي ملف تنفيذي إلى هدف التطبيق.

| حزمة عامة جرى فحصها | ما رصده الجرد | معرّف دليل REA |
|---|---|---|
| `sqlite-jdbc-ios-3.41.0.0.jar` | 127 ملفًا، منها 115 ملف class؛ لا أسماء ملفات تنتهي بـ `.so` أو `.dylib` أو `.a` داخل الجرد | `ev_504976812d913921601280077143daa1533e264574b031869a77a3a90d29bacd` |
| `cloud-api-1.0.0.jar` | 45 ملفًا، منها 41 ملف class؛ تتضمن أسماء نماذج `app/tachimanga/cloud` | `ev_94564f6b38da46d198e62f52087c3efe1cec00fe16c5c77537d1ae8cd313523f` |

تغطية الحاويتين `container-entries: complete` ضمن حدود الأداة. الجرد لا يثبت استدعاء صنف أو تحميل مكتبة، ولا يحوّل وجود حزمة API إلى تنفيذ سحابة متاح أو مرخص للنسخ. غياب امتدادات native في هذه الحزمة وحده لا يثبت غياب ربط native خارجها.

نجح `inspect-artifact` دون تشغيل الحزم. تعطل `doctor --client codex` لأن `ps` لا يستطيع قراءة معلومات العملية في هذه البيئة (`fatal library error, lookup self`). حُفظ التشخيص في `validation/rea/doctor.json`؛ لم تُغيَّر حدود البيئة أو يُتحايل عليها. هذا لا يلغي نجاح الجرد الساكن، ولا يثبت جاهزية أدوات التنفيذ أو التفكيك العميق.

## كيف تتوزع مكونات Tachimanga بحسب الأدلة

| الطبقة | الدليل ونوعه | ما نستفيد منه في MangaShelf |
|---|---|---|
| واجهة Flutter | **تقرير سابق فقط** في `ARCHITECTURE-AR.md`؛ لم تُفحص عينة الواجهة مجددًا | الاحتفاظ بواجهة SwiftUI الحالية مع قياس السلوك بصريًا على جهاز |
| منطق Kotlin/Java وطبقة توافق Android | سورس الخلفية العام: `server/` و`AndroidCompat/` | فصل محرك المصدر عن المكتبة والعرض، وفهم واجهات الإضافات قبل ربطها |
| تحميل أصناف JAR | `PackageTools.loadExtensionSources0` يستخدم URLClassLoader أو بدائل ChildFirst، ثم reflection | فحص الحزمة لا يعادل تحميل الصنف أو نجاح مصدر؛ يلزم محرك وتبعيات فعلية |
| الشبكة عبر NativeNet | `NativeNet.java`: JSON UTF-8 وOkio Buffer للطلب، ثم مصفوفتان للرد: metadata وbody | احترام طول كل مصفوفة والفشل عند جسم غير صالح بدل إرسال طلب ناقص |
| أحداث NativeChannel | `NativeChannel.java`: topic وcontent كمصفوفتي UTF-8؛ `JavaChannel.kt` يوضح عمليات أخرى باتجاه Java | عدم اعتبار الحدث النصي إثباتًا لوصوله إلى Swift؛ الجسر يحتاج ربطًا واختبارًا مستقلين |
| محرك OpenJ9 التفسيري | **دراسة العينة السابقة** في `RUNTIME-REFERENCE.json` تشير إلى `_J9_CreateJavaVM` وخيار `-Xint` | لا نفترض أن OpenJDK Zero الحالي هو المحرك نفسه أو أن مكتباتهما قابلة للتبادل |

المقارنة أعلاه تستعمل السورس لتحليل الأجزاء المفتوحة، وREA للحزم المنشورة. لا يوجد داعٍ لتفكيك سورس واضح عبر أداة ثنائيات، ولا ادعاء باستعادة مشروع Dart أو تعديلات OpenJ9 الخاصة بـiOS.

## الإصلاحات في هذه الجولة

1. **نتائج المحرك:** أزيل fallback الذي كان يختلق عناوين وفصولًا وصفحات ويعلن تحميل الإضافة عند غياب JVM. أصبح غياب المحرك خطأً واضحًا مترجمًا. بيانات الاختبار موجودة في هدف الاختبارات فقط عبر حقن dispatcher.
2. **أوامر JSON:** توليد جميع payloads باستخدام JSONSerialization؛ تبقى علامات الاقتباس والشرطة العكسية والأسطر والعربية كما هي. لا تتغير حالة loadedPackages إلا بعد إقرار صحيح بالتحميل أو الإزالة.
3. **روابط المصادر:** أضيف sourceURL اختياري للعناوين والفصول، وحُفظ خلال البحث والتفاصيل والتخزين والتنزيل. يُرسل رابط المصدر الأصلي إلى المحرك بدل اختراع `/manga/<id>` و`/chapter/<id>`. البيانات القديمة تظل قابلة للقراءة؛ الرابط المفقود لا يُخمن.
4. **حالة جسر C:** فصل تسجيل dispatcher عن إيقافه، ومنع الاستدعاءات اللاحقة بعد تعطيله، وتصفير مخرجات الفشل كي لا تُستهلك قيم قديمة.
5. **حدود NativeNet:** رفض أجسام الطلب والرد غير الصالحة أو المتجاوزة للحدود، ومعالجة استثناءات JNI وعدم إرجاع نجاح جزئي مع جسم مفقود. اختبارات هذه الحدود تستعمل أصناف Java اصطناعية من المشروع.

تفاصيل النتائج المنفذة في `validation/`. اختبارات Swift المضافة تغطي غياب المحرك، إقرارات دورة الحياة، ترميز النصوص، وحفظ روابط المصادر بعد إعادة فتح المكتبة؛ لم تُشغّل هنا لغياب Swift وXcode.

استدعاء dispatcher الأصلي لا يُعاد تلقائيًا عند امتلاء الرد، لأن إعادة الاستدعاء قد تكرر تحميلًا أو إجراءً آخر داخل Java. يحتفظ المسار التجريبي حاليًا بمخزن 16,384 بايت، ويرفض الرد الأكبر أو غير المنتهي بـNUL أو غير الصالح كـUTF-8. دعم الردود الأكبر يحتاج واجهة تسترجع الرد المحفوظ دون إعادة تنفيذ الأمر؛ حد المخزن لا يخص جسم HTTP الثنائي المنفصل.

التحقق المنفذ لهذه المراجعة: 34 اختبار أرشيف C، و7 اختبارات تغليف، و9 اختبارات جديدة لجسر C نجحت في البناء الصارم ومع ASan/UBSan. أضيفت 27 حالة حدود NativeNet ضمن اختبار JVM المضيف ونجحت مع `-Xcheck:jni`، ومع بناء C صارم وASan/UBSan. نجح كذلك فحص الأرشيف بـ30,000 مدخل عشوائي و30,000 طفرة وفحص الموارد. هذه مجموعات مختلفة؛ لا تمثل عدد اختبارات Swift أو ميزات iOS الناجحة.

## العمل المتبقي وترتيبه

1. توفير العينة المرجعية الأصلية كملف محلي صريح، وتسجيل الإصدار والحجم والبصمة، ثم `inspect-artifact` وقراءة Info.plist وخرائط المكتبات. يلزم مزود يدعم ARM64 Mach-O للتفكيك العميق. جرد JAR الحالي ليس بديلًا عن هذه الخطوة.
2. إثبات محرك Java مبني من مصدر معروف على **جهاز iPhone**: بدء VM وتحميل JAR اصطناعي وreflection وخيوط وملفات. نجاح VM المضيف أو إنشاء ملف ARM64 لا يكفي.
3. ربط `ms_java_*` و`ms_bridge_*` بعقد واحد واضح للأطوال والملكية والإلغاء. حاليًا هما واجهتان منفصلتان، ولا يوجد مسار إنتاج مثبت يبدأ JVM ويسجل dispatcher.
4. ربط StagedExtensionStore بالمحرك والتحقق من SHA قبل التحميل، وإيقاف المحرك عند إلغاء الثقة أو إزالة الإضافة. قراءة `isTrusted/isActive` في الواجهة وحدها لا تحقق هذا الربط.
5. عرض `ExtensionRecord.sources` بمعرّفات مصادرها؛ packageName ليس sourceId وقد تحتوي الإضافة أكثر من مصدر. ثم إثبات مسار مصدر واحد: بحث ← تفاصيل ← فصول ← صور على iPhone.
6. معالجة إلغاء مهمة NativeBridge عند انتهاء مهلة الانتظار، ثم تخزين الإصدارات السابقة لاسترجاع فعلي. الدالة المسماة rollback حاليًا تزيل السجل التالف ولا تستعيد نسخة سابقة.
7. بعد ذلك تُختبر التنزيلات والخلفية والذاكرة والواجهة بالعربية والإنجليزية، ويُحدَّث سجل الميزات بنتائج جهاز فعلية. تبقى ملاحظات «اكتمال المرحلة الثانية» القديمة تاريخية وغير كافية لإثبات هذه البوابات.

## إعادة التحقق

من جذر MangaShelf:

```bash
python3 scripts/test_native.py
python3 scripts/run_sanitizers.py
python3 scripts/test_packaging.py
python3 scripts/test_bridge.py
python3 scripts/check_ui_resources.py
python3 scripts/audit_project.py
```

اختبار JNI يتطلب JDK المضيف وملفات ترويساته؛ الاختبارات تشغل fixtures المشروع فقط:

```bash
python3 scripts/build-native-runtime-probe.py --java-home /path/to/jdk
```

وعلى macOS/Xcode 26 قبل الدمج:

```bash
swift test
bash scripts/build-ios.sh simulator
bash scripts/build-ios.sh unsigned
```

لا يوجد في هذا التسليم بناء IPA جديد أو نتيجة تشغيل iPhone. نجاح C أو فحص الموارد لا يثبت ترجمة Swift أو المطابقة البصرية.

في بيئة هذه الدراسة تعذر LeakSanitizer بسبب قيود قراءة `/proc`؛ نجح اختبار الجسر مع ASan/UBSan عبر `python3 scripts/test_bridge.py --no-leak-check`. المحاولة المقيدة ونتيجة النجاح محفوظتان منفصلتين. هذا لا يُعد نتيجة فحص تسرب ذاكرة.
