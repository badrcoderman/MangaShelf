# فحص توقيع JAR قبل تنفيذ الإضافات

أضيف `ExtensionArchiveVerifier` كفاحص مستقل للبيانات على المضيف؛ لا يحمل
أصناف الأرشيف ولا يستدعيها، ولم يوصل بمسار الإنتاج في MangaShelf.
هذا تقدم جزئي في ENG-09، وليس إثبات تشغيل مصدر أو إثبات هوية ناشره.

## العقد

يقدم المستدعي مسار JAR، وبصمة SHA-256 متوقعة لكامل الملف، وبصمة SHA-256
لشهادة الموقّع الطرفية بصيغة DER يثق بها مسبقًا، ومجلد عمل قابلًا للكتابة
داخل حاوية التطبيق. لا يستخرج الفاحص الثقة من شهادة الحزمة نفسها.

ينشئ الفاحص نسخة مؤقتة محدودة الحجم، ويحسب بصمتها أثناء النسخ، ثم يفحص
أسماء ZIP الفعلية وتفردها وأحجامها وCRC قبل فتح `JarFile` مع التحقق.
يقرأ كل ملف حتى EOF قبل طلب `getCodeSigners()`، ويشترط موقّعًا واحدًا
تطابق شهادته البصمة الصريحة في كل حمولة؛ تشمل السياسة ملفات الخدمات
والموارد والنسخ المتعددة داخل META-INF. يستثني manifest وملفات التوقيع
القياسية المقترنة فقط، والأدلة الفارغة.

الحدود الحالية: 64 MiB للأرشيف، و4096 مدخلًا، و16 MiB لكل حمولة، و128 MiB
إجماليًا بعد الفك، و1 MiB لكل ملف metadata خاص بالتوقيع. تبقى خوارزميات
التوقيع الخاضعة لسياسة Java المعطلة معطلة.

تحذف `verify` النسخة المؤقتة وتغلقها قبل الرجوع. النتيجة تصف تلك النسخة؛
لا تجيز تحميل المسار الأصلي لاحقًا لأنه قد يتغير. أضيفت `openVerified`
لإبقاء JarFile نفسها مفتوحة بعد حذف اسم النسخة الخاصة، ثم يستخدم
[محمّل المصادر](VERIFIED-EXTENSION-LOADER-AR.md) المقبض نفسه حتى نهاية
العمليات. يتطلب ذلك POSIX وحذف ملف مفتوح، وما زال خارج هدف iOS الرئيسي.

## التحقق المنفذ

شُغّل `python3 scripts/test-extension-archive-verifier.py` على Java 27، مع
ترجمة `--release 17 -Xlint:all -Werror`. نجحت 47 حالة بمفاتيح وأرشيفات
اختبار أنشأها المشروع، تشمل العبث بالمحتوى وmanifest، والبصمة والشهادة
الخاطئتين، والحمولات غير الموقعة داخل META-INF، وتعدد الموقّعين، والأسماء
المكررة وغير الآمنة، وحدود الأحجام وتنظيف الملفات المؤقتة. تشمل الإضافات
اختبار موقّعين منفصلين وتلف CRC وحجم معلن أصغر من البيانات المفكوكة.
[التقرير والأوامر والبصمات](../validation/extension-archive-verifier-host.json).

أعيد إنتاج مشكلة ترتيب المدخلات: فقد `JarInputStream` معلومات الموقّع
حين سبقت الحمولة manifest، بينما تحقق `JarFile` من الملفات نفسها. يوضح
[عقد JarInputStream](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/jar/JarInputStream.html)
قيود ترتيب metadata، ويوضح
[JarEntry](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/jar/JarEntry.html)
أن معلومات الموقّع تتاح بعد قراءة المدخل كاملًا.

فُحصت حزمة MangaDex المعاد بناؤها من المصدر العام في `39768470880`
كبيانات توقيع فقط: 159 مدخلًا، منها 156 حمولة موقعة و505152 بايت بعد الفك.
استُعملت بصمة شهادة **Android Debug للتشخيص فقط**، لا بوصفها ثقة بالناشر؛
لم يُحمّل أو ينفذ أي صنف منها.

## المتبقي

- توفير مفاتيح ناشرين موثوقة بسياسة اعتماد وتحديث وسحب واضحة؛ لا يكفي hash
  أو مفتاح مستخرج من الحزمة أو قبول شهادة debug.
- ربط محمّل المقبض المتحقق بمخزن staging في Swift؛ اجتاز مسار المضيف
  اختبار استبدال الملف الأصلي بعد الفحص بحزم مؤلفة للمشروع.
- إعادة الفحص عند التحديث ومنع التحميل وإزالة المصادر عند سحب الثقة.
- تجربة الفاحص ومقدمي التشفير على صورة Java المبنية لـiOS، ثم إثبات مصدر
  حقيقي على iPhone؛ نجاح المضيف لا يثبت ذلك.

يتحقق
[JarFile](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/jar/JarFile.html)
من التوقيع الرقمي، ولا يؤسس ثقة سلسلة الشهادات. سياسة بصمة الشهادة هنا لا
تدعي تحقق PKIX أو الصلاحية الزمنية أو الإلغاء أو سلامة كود الإضافة.
